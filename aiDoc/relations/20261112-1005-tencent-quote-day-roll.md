# 腾讯报价的「行情日」：09:15 滚动，取错字段会静默错标

日期：2026-11-12
范围：`market.valuation_snapshot` / 腾讯源 / `app.data_sources.tencent` / `app.services.tencent_valuation_collection`
状态：已修复、已清理污染数据、已实跑验证

---

## 1. 故障现象

2026-11-12 同步腾讯估值时发现：**只有 435 / 5,573 行通过闸门（7.8%）**，
5,138 行被 `price_mismatch` 拒绝。

第一直觉是「数据有问题」。实际是**真 bug**，而且是最难查的那一类：
**失败是静默的，错的那部分看起来完全正常**。

---

## 2. 根因：两个价格字段都相对「行情日」定义，而行情日在 09:15 滚动

腾讯报价端点给两个价格：

- `price` —— **行情日**的价格（盘后/盘前是该日收盘的冻结值，盘中是实时 tick）
- `last_close` —— **行情日前一个交易日**的收盘

关键在于**行情日在 09:15（集合竞价开始）滚动，不是午夜**。实测同一只股票：

| 观测点 | `price` | `last_close` |
|---|---|---|
| 09:03 竞价前 | 11-11 收盘 | 11-10 收盘 |
| 09:19 竞价中 | 实时 tick | 11-11 收盘 |
| 15:24 收盘后 | 11-11 收盘 | 11-10 收盘 |

原实现把 `close_field="last_close"` **写死**在采集服务里。于是：

- 15:24 跑（11-11 收盘后）：行情日 = 11-11 → `last_close` = 11-10 收盘 → 目标 11-10 **日期对**
- 09:03 跑（11-12 竞价前）：行情日 = 11-11 → `price` = 11-11 收盘 → 取 `last_close` 拿到的是 **11-10 收盘** → 目标 11-11 **日期错**

错字段照样给每只股票一个**看似合理**的价格，只是属于另一个交易日。
价格闸门（与可信收盘比对）把 5,138 行挡掉了，于是故障表现为
「**覆盖率只有 7.8%**」而不是「日期错了」——这是最坏的呈现方式：
看指标像是数据源掉线，看代码像是参数没调好。

---

## 3. 证据链

### 3.1 派生量恒跟 `price` 走

`mcap_yi` / `float_mcap_yi` / `pe_ttm` / `pe_static` / `pb` 都是按**行情日价格**
算的，不是按 `last_close`。两条独立判据：

| 判据 | 结果 | 结论 |
|---|---|---|
| `mcap / price` 反推股本 | 194.059025 亿股 ≈ 真值 194.0592 | 市值跟 **price** |
| `mcap / last_close` 反推 | 193.727583 亿股（偏 0.17%） | 反证 |
| EPS 跨时刻恒定（用 price 反推） | 中位 **0.0075%**（P90 0.0416%） | PE 跟 **price** |
| EPS 跨时刻恒定（用 last_close 反推） | 中位 **0.615%**（P90 3.26%） | 反证（差 82 倍） |

**唯一例外**：`limit_up` / `limit_down` 按 `last_close`（11.71 × 1.1 = 12.88），
因为交易所用前收盘定涨跌停价。

### 3.2 照抄派生量会让行内自相矛盾

即使日期对了，直接照抄厂商的市值也会出事：那一行的 close 属于一个交易日，
市值属于下一个。11-10 那批 5,561 行就是这样——
`mcap / 行close` 反推股本 = 191.60 亿股，而 `mcap / 11-11 收盘` = 194.0589 亿股
（≈ 真值 194.0592）。**行内数字互相打架**。

### 3.3 `is_stale` 的语义与它的失效条件

厂商的僵尸报价判据是 `amount_wan == 0 and price == last_close and price > 0`。
这是**数值比较**，所以字段的日期归属不影响它本身——但它意味着「行情日没有成交」，
而**行情日是不是目标日，取决于选了哪个字段**：

- `price` 口径：行情日 == 目标日 → 定格报价意味着目标日无成交 → **丢弃**
- `last_close` 口径：行情日 == 目标日的下一个交易日 → 目标日的收盘仍然是真的
  → **保留**，交给可信收盘闸门裁决

## 4. 污染量化（修复前的实际数字）

```
trade_date=2026-11-10  close 精确等于 11-10 收盘 : 5561   日期对，口径混合
trade_date=2026-11-11  close 精确等于 11-10 收盘 :  226   错标
trade_date=2026-11-11  close 精确等于 11-11 收盘 :  209   日期对（含 208 个两日同价）
```

> 计数口径提醒：判定「这行属于哪一天」的容差**必须小于一个最小跳动（0.01）**。
> 用 0.011 时，相邻两天的收盘价在只差一分钱的情况下会互相匹配，
> 于是「错标数」会被算成 0（本次就踩过一次）。

## 5. 修复

### 5.1 取哪个字段由行情日归属决定，并**实测校验**

`app/data_sources/tencent.py`：

```python
QUOTE_DAY_ROLL = time(9, 15)

def close_field_for_quote_day(now, *, today_is_trading_day: bool) -> CloseField:
    if today_is_trading_day and now.time().replace(tzinfo=None) >= QUOTE_DAY_ROLL:
        return "last_close"
    return "price"
```

规则来源：目标日 = **严格早于当前北京自然日**的最后交易日，于是厂商的行情日
要么就是目标日（`price`），要么是目标日的下一个交易日（`last_close`）。
后一种情况当且仅当「今天是交易日 且 已过 09:15」。

`close_field` 在 `to_valuation_records()` 里**没有默认值**——强制调用方显式决定，
杜绝「写死」这种失败模式复现。

### 5.2 一致性守卫：规则不是保证，是待检验的假设

采集服务把两个字段都拿去和**可信收盘**比，选中字段的一致率低于 50% 就
**中止运行并报错**。厂商行为若变（换 roll 时刻、换字段语义），故障会变成
一次响亮的失败，而不是一批错日期的行。

实测（2026-11-12 09:59 盘中）：

```
取价字段   : last_close
字段一致率 : last_close=99.82%  price=8.02%
```

### 5.3 派生量一律重述到所选收盘口径

```
mcap_new = mcap_vendor × close / price        （先乘后除，只做一次除法）
```

股本 / 每股收益 / 每股净资产在一次报价内不变，所以这个缩放**恒等**——
无论 `price` 属于哪个会话都成立。每行写入前检查**股本守恒**：
`mcap / close` 必须还原出厂商那个股本。

### 5.4 目标日语义显式化

只观察**严格早于当前北京自然日**的最后交易日：21:00 跑采昨天，跨 0 点后才采
新的一天。顺带修掉一个既有缺陷：不传 `trade_date` 时服务会拿今天当目标并直接
抛错，与它自己文档里「由服务判定」的说法矛盾。

## 6. 数据修复

新增 `scripts/maintenance/repair_tencent_valuation_caliber.py`，两个动作，默认演练：

| 动作 | 作用 | 结果 |
|---|---|---|
| `--action misdated` | 删除 close 属于其他会话的行 | 11-11 删 **226** 行 |
| `--action caliber` | 把市值/PE/PB 重述到本行收盘口径 | 11-10 修 **5,353** 行 |

两条硬性设计：

1. **换算从 raw_payload 的原始值重算**，不依赖库里现存的值 → 脚本可重复运行；
   幂等判定用相对容差（1e-9），否则末位舍入会让脚本每次都「有得改」。
2. **重述是恒等式**：`mcap = shares × price` ⇒ `shares × close`。所以某只股票
   在下一交易日停牌（没有下一交易日的可信 bar）时**照样能重述**，不必跳过。

修复后独立复算：

```
2026-11-10: 5561 行 | close 精确等于可信收盘 5561/5561
                   | 重算一致 5561/5561 | 股本守恒失败 0（最大偏差 6.2e-15）
2026-11-11: 5563 行 | close 精确等于可信收盘 5563/5563
                   | 重算一致 5563/5563 | 股本守恒失败 0（最大偏差 6.0e-16）
```

## 7. 硬规则（下次动这块之前先查）

1. **两个价格字段都相对「行情日」，行情日 09:15 滚动。** 任何时候都不要写死
   `last_close` 或 `price`，用 `close_field_for_quote_day()`。
2. **凡是「多源对账/价格闸门突然大面积拒绝」，先怀疑口径而不是数据源掉线。**
   本次 92% 的行被拒，根因是取错了字段——闸门是对的。
3. **区分「属于哪一天」的容差必须 < 0.01。** 0.011 会让相邻交易日互相匹配。
4. **厂商给的市值/PE/PB 是价格口径的**，跟任何别的字段放在一起前先重述。
   `limit_up`/`limit_down` 是唯一按前收盘算的例外。
5. **区分会话要用精确相等 + 独立的下一交易日校验**，不要只看「日期对不对」——
   11-10 与 11-11 同价的那 208 行，两种口径下都「看起来对」。
6. **Windows 上的 Git Bash `date` 不解析 IANA 时区名**（`TZ=Asia/Shanghai date`
   给的是错的）。判断上海时间一律用 `datetime.now(ZoneInfo("Asia/Shanghai"))`。
7. **纯数字观测比文档可靠**：厂商字段语义只能靠「同股跨快照反推股本恒定性」
   这类**不依赖日期归属**的判据来锁定。
