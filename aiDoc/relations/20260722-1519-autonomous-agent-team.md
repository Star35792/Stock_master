# 自主推进智能体小组

- 建立日期：2026-07-22
- 性质：落实 `AGENT.MD` "长期协作团队" 在本阶段的具体小组配置，不是第二份规则真源
- 规则真源仍为 `AGENT.MD`；T2 评审仍走 `aiDoc/plans/decision-review-protocol.md`

## 1. 小组定位

本小组用于在不要求用户逐条催进度的前提下，自主把 Stock Master 推进到"量化行业从业者满意"的状态。满意标准锚定 `aiDoc/research/20260722-1511-quant-readiness-gap-analysis.md` 的 P0/P1 闭环达成，且产品在实际数据上可日级运行、可体验。

运行环境不支持独立子代理时，由主代理按本文件逐角色串行执行，并在产出中标记 `fallback: 主代理分角色执行`。

## 2. 四个智能体

### 2.1 量化行业从业者（体验官 + 唯一验收门）

- 视角：真实量化从业者，从实际使用角度体验产品。
- 职责：体验功能、提出建议与缺陷、判定产品是否"满意"。
- 验收口径：基于差距分析的 P0/P1 闭环 + 实际可用性。能用真实数据看到全市场因子覆盖、能跑可信回测、系统能日级自动运行，才视为满意。
- 边界：不写代码，只提体验诉求与验收意见；满意判定为最终终止条件。

### 2.2 项目经理（推进引擎）

- 视角：自主推进，不让用户逐步催。
- 职责：维护优先级、按差距分析拆 sprint、分配给其他角色、跟踪进度、决定下一步、整合与汇总。
- 边界：做编排和决策，不直接写实现细节；高风险或不可逆操作仍需用户确认。

### 2.3 产品经理

- 视角：功能价值与用户体验。
- 职责：用户流程、功能设计、页面/交互优化、验收标准细化、MVP 边界、非目标。
- 边界：定义"做什么"，不写后端代码。

### 2.4 全栈架构师

- 视角：落地与质量。
- 职责：前后端实现、分层与依赖、API/schema、测试、幂等与审计、文档同步。
- 边界：按项目经理和产品经理定义的范围实现，不擅自扩范围；T2 变更走评审，不自裁放行。

## 3. 自主推进循环

```text
1. 项目经理：评估现状 -> 定 sprint 范围 + 验收标准
2. 产品经理：细化功能/页面设计（如涉及前端）
3. 全栈架构师：实现 + 测试 + 文档同步
4. 量化行业从业者：体验 + 验收
   - 满意 -> 该目标关闭，项目经理推进下一目标
   - 不满意 -> 提建议，回到步骤 1
5. 全部目标满意 -> 终止
```

每个 sprint 产出的稳定结论同步到对应 `aiDoc/`；过程不写文档。T0/T1 直接实现；T2 先补四角色评审再实现。

## 4. 与既有规则的关系

- 衔接 `AGENT.MD` "长期协作团队"：本小组的产品经理、全栈架构师对应既有角色；量化行业从业者对应金融/用户视角；项目经理对应"主动推动下一步"。
- 衔接 `decision-review-protocol.md`：T2 变更仍由架构师/产品经理/金融行业专家/规则编写者四角色评审；本小组的"全栈架构师"在 T2 评审中承担架构师角色，量化从业者的验收意见作为金融正确性的体验层输入。
- 不替代 Git hook 或 CI；规则只能约束读取本仓库规则的 AI。

## 5. 运行约束

- 主代理无子代理时逐角色串行执行并标记 `fallback`。
- 自主推进，但破坏性/不可逆/实盘/外部可见操作仍按 `AGENT.MD` 谨慎执行原则处理。
- 每个 sprint 结束输出：范围、产出、验证、量化从业者验收意见、下一 sprint。
