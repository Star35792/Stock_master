# 行业时点事实落地：从「当前标签回填」到真实变迁史

> 日期：2026-11-11
> 关联任务：#12 修复行业标签前视偏差
> 状态：已交付并验证

## 一句话

`market.security_industry_history` 从「每标的 1 条、`effective_to` 全 NULL、
行业名等于当前标签」的假历史，换成申万归属变动表给出的 **11,963 条真实生效
区间 / 5,585 只标的**；三族行业因子与估值行业内分位全部按目标交易日的时点
标签重算，并**用原始 bar 独立复算验证到逐行一致**。

## 为什么要做

`market.security.industry` 只存**当前**行业标签。任何按目标交易日做 as-of
匹配的历史读取，拿到的都是今天的行业归属——一个 2024 年才被划进「银行Ⅱ」的
股票，在 2020 年的横截面里也会被当成银行股参与行业中性化。

落地前的实测量级：

| 项 | 值 |
|---|---|
| 历史表行数 | 5,579（每标的恰好 1 条） |
| `effective_to` 非空 | **0** |
| 行业名与当前标签逐字相同 | **100%** |
| 读取端 as-of 解析结果 | 恒等于当前标签 |

即：整个时间轴被压成了「行业从未变更」这一个假设。

## 数据源与口径

**申万宏源《申万行业分类标准（2021 年版）》个股归属变动表**

```
https://www.swsresearch.com/swindex/pdf/SwClass2021/StockClassifyUse_stock.xls
```

行结构 `(股票代码, 计入日期, 行业代码, 更新日期)`，其中 **「计入日期」就是该次
归属的生效日**——这正是时点事实的来源。实测 12,934 行 / 5,938 只标的，
**2,024 只历史上变更过行业**，最多的一只变更过 10 次。

### 代码结构

申万 2021 分类的 6 位代码：**前 2 位 = 一级，前 4 位 = 二级，后 6 位 = 三级**。
项目标签粒度是二级，映射键取前 4 位。

### 中文名从哪来

申万只发布代码、不发布中文名，而项目的 `market.security.industry` 存的就是
申万二级行业名。所以名字只能**从项目已有标签反推**：取「当前归属该二级代码」
的标的在项目里的行业名众数。

**但反推只对「当前仍有人在用」的二级代码可行**：

| 二级代码类别 | 数量 | 处理 |
|---|---|---|
| 当前仍有标的在用 | 131 | 反推中文名 |
| 2021 版之前的遗留码 | **63** | 回退成 `申万-<代码>` |

遗留码（如 `4401` 是 2021 版之前的「银行」，`4801` 是 2014–2021 的银行分类）
当前没有任何标的在用，无从反推。这些区间**保留为 `申万-<代码>` 而不是丢掉**：
丢掉会让时间线出现空洞（等于让标的在早期区间回退到今天的标签——那正是本次
要消除的偏差）；保留则会在行业分组里出现稀疏的伪行业，这在口径上是诚实的。

**关键结论**：这 2,797 个回退标签区间**全部止于 2021-07-30**（申万改版日），
即 2021-07-30 之后只有现行申万 2021 名称。**近期（2026）因子计算完全不受
遗留码影响**，历史与当前口径不可比的范围被限制在 2021 年之前。

## 实现要点

### 1. 6 位代码消歧

申万表只给 6 位代码、不带交易所，而 6 位代码在 SH/SZ/BJ 存在碰撞（实测 108
个）。碰撞码只能用「首次计入日期 == 上市日」匹配；仍无法确定的**跳过并计入
报告**，绝不猜。实测本次：歧义 0、未匹配 353。

### 2. 上市日钳位与键去重

申万历史可能早于本项目记录的上市日（退市/借壳/口径差），钳位到上市日。
**钳位会把多条记录压到同一天**——实测 30 只标的（如 `002259.SZ`、`300214.SZ`）
因此产生同一个 `effective_from`。压到同一天时保留**原始计入日期最晚**的那条：
那是上市时点实际生效的分类；更早的那条区间被压缩成零长度，本来就不该存在。

> 顺序很关键：**先钳位、再去重**。先去重后钳位会漏掉这个冲突。

### 3. DuckDB 的唯一索引在同一事务内不释放已删除的键

这是本次踩到的最硬的一个坑，表现为：

```
Constraint Error: Duplicate key "symbol: 000001.SZ, effective_from: 1991-04-03"
violates unique constraint.
```

排查过程（每一步都排除了一个假设）：

1. 计划内重复键 → **0**；
2. 原始 DuckDB 在内存库同事务 delete+insert → **正常**；
3. 真实库上原始 SQL 复现 → **复现**；
4. 删除并提交后在新事务插入 → **正常**。

结论：**DuckDB 的唯一索引在同一事务内不清理已删除的键**，跨事务才正常。
这不是本项目的偶发脏数据，是 DuckDB 的索引行为。

因此写入改成两步、两笔事务，**任何一步都不做「同事务 delete + 同键 insert」**：

1. **upsert 计划区间**（`ON CONFLICT (symbol, effective_from) DO UPDATE`）；
2. **清理孤儿行**：申万覆盖到的标的里，旧回填行的 `effective_from` 可能不在
   计划内（例如申万历史晚于上市日），留着它等于在早期区间继续用今天的标签。
   这些行按「不在计划键集合内」判定后单独删除。

两步都可重复执行（幂等）。

### 4. 读取端：按目标交易日解析

新增 `SecurityIndustryHistoryRepository.load_intervals()`（一次取回全部区间）
与模块级 `resolve_industries_by_date()`（内存内二分定位生效区间）。

**为什么要有批量入口**：`industries_as_of` 每查一个交易日发一次带 5,585 个
symbol 的 IN 子句。两年回测约 500 个交易日 → 500 次全表扫描。

接入的三处：

| 服务 | 改前 | 改后 |
|---|---|---|
| `factor_cross_section.py` | `get_industries()` 单一映射（当前标签） | 按交易日 `industries_by_date` |
| `valuation_factors.py` | `get_industries()` 单一映射 | 按交易日 `industries_by_date` |
| `industry_factors.py` | 逐日 `industries_as_of()` | 批量加载 + 内存解析 |

回退到当前标签是**显式行为**：没有历史区间覆盖的标的才回退，且回退在代码里
可见、并在 run 元数据里记录。

### 5. 采集可靠性：重试 + 本地缓存

源站点在本机/企业网环境下证书链不完整（`certifi` 覆盖不到），且**代理 502 是
常态**（交付当天就遇到一次 `ProxyError: Tunnel connection failed: 502`）。因此：

- 默认**校验证书**，提供显式 `--insecure` 开关（akshare 官方库对同站点接口
  同样使用 `verify=False`）；
- 抓取带**退避重试**；证书错误立即失败（重试无意义）并给出可执行提示；
- 下载内容落**本地缓存**（`data/cache/sw_industry/`，带 sha256 与抓取时间），
  默认复用；`--refresh` 强制重下；网络失败但本地有缓存时回退到缓存。

> 缓存不是为了省流量，而是为了保证 **dry-run 审查的计划 == 实跑执行的计划**。
> 每次都重新下载的话，两次读到的可能是不同快照，「先看计划再落库」就失去意义。

## 被污染数据的处理

落地前的行业因子值全部是污染的：315,453 行。

| 因子 | 行数 | 污染来源 |
|---|---|---|
| `industry_momentum_60` | 100,595 | 行业分组来自历史表（当时全是回填行） |
| `industry_breadth_20` | 100,595 | 同上 |
| `industry_turnover_share_change_20` | 100,595 | 同上 |
| `industry_valuation_gap` | 13,668 | 行业分组来自 `market.security.industry` |

处理方式（`scripts/maintenance/clear_contaminated_industry_factors.py`）：

1. 导出 Parquet 备份到 `data/backups/industry_factor_contamination_20261111.parquet`；
2. 删除；
3. 用 PIT 口径重算（`--code-version sw-industry-pit-v1`）。

**顺带查清的一件事**：旧值不是一次运行的结果，而是 **5 次不同回看窗口的运行
拼凑**（run 391/462/1250/1323/1414，input_start 分别是 2026-05-28 /
2026-06-14 / 2026-06-03 / 2026-06-22 / 2026-06-24）。所以新旧值差异里混着
「口径变化」和「窗口变化」两个因素——这也是为什么必须做独立复算校验而不是
直接对比新旧值。

## 验证

### 独立复算（最强证据）

`scripts/maintenance/verify_industry_factors.py` **绕开因子服务**，只用原始
数据重算一遍：从 `market.daily_bar` 取每只标的窗口内第 N+1 根与第 N−59 根的
收盘价比，按时点行业聚合，再与落库值逐行比对。

```
--- industry_momentum_60 ---
  落库行数     : 55701
  可比对行数   : 55701
  完全一致行数 : 55701
  最大绝对偏差 : 4.99e-11
  最大相对偏差 : 8.30e-08
--- industry_breadth_20 ---
  落库行数     : 139159
  可比对行数   : 139159
  完全一致行数 : 139159
  最大绝对偏差 : 4.95e-11
```

**逐行完全一致**，最大偏差 5e-11（Decimal 量化级）。

> 写这个校验脚本时自己也踩了一个坑：相关子查询取的是「前一根 bar」（1 日收益）
> 而不是「前 60 根」，第一版校验全表不匹配。**校验脚本自己也必须被校验**——
> 否则会误报「数据错了」。

### 表结构自洽

| 检查项 | 结果 |
|---|---|
| 总行数 / 标的数 | 11,963 / 5,585 |
| 唯一键重复 | **0** |
| 同标的区间重叠 | **0** |
| 每标的区间数分布 | 1 条 1,940 / 2 条 2,024 / 3 条 901 / … / 10 条 3 |
| 遗留码区间时间上界 | 2021-07-30 |

每标的区间数分布与申万源表的变更次数分布一致。

## 遗留与后续

1. **119 只标的（2.1%）的时点标签与项目当前标签不一致**，例如
   `603336.SH`（项目「种植业」/ 申万「化学制药」，申万归类日 2026-09-24）、
   `688117.SH`（项目「生物制品」/ 申万「化学制药」）。数据源是申万，权威性
   更高；但项目当前标签的来源需要单独核对，是**另一个数据一致性问题**。
2. **控制面 `market.daily_bar` 只有 2026-07-28 起的 71 个交易日**，所以 60 日
   动量最早只能算到 2026-10-28（`industry_momentum_60` 只有 10 个交易日
   55,701 行，而 20 日宽度的 `industry_breadth_20` 有 25 个交易日 139,159 行）。
   要更长窗口需要补 bar 历史。
3. **`data/backup_altdata/stock_master-20261111-1628.duckdb` 是空壳**（1.6 GB
   文件但 0 张表）——多半是在主库有未提交事务时复制出来的。真正的整库备份在
   `data/backups/`（`stock_master-pre-compact-20261109-082805.duckdb` 等）。
   **不要依赖 `backup_altdata/` 目录**。
4. `market.security_industry_history` 尚无 `industry_code` 列，中文名与二级
   代码的对应关系只存在于采集期的内存映射里。跨行业迁移分析（例如「从哪个
   行业迁到哪个行业」）需要补一列存 6 位代码。
