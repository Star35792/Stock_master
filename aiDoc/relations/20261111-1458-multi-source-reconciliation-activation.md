## 一、三条被写死的口径规则

对账不是"两个源比一下"。实测（2026-11-10，通达信 vs 同花顺，6,125 个可比标的）暴露了三种
性质完全不同的差异：

| 现象 | 样本 | 性质 |
|---|---|---|
| 收盘价差 0.005 元 | 5,620 个精确相等，其余为小数位精度差 | 舍入，不是冲突 |
| 成交量差精确 100 倍 / 10000 倍 | 541 + 2 只指数 | 单位口径差，不是冲突 |
| 成交量差 105.4 / 108.7 / 112.4 倍 | 3 只 LOF 基金 | 份额折算，不是冲突 |
| 成交额差 50.4% | 399002.SZ「深成指R」 | **真实数据不一致** |

### 判据的核心：成交额是锚

A 股 `成交额 = 均价 × 成交量`。因此：

- **两边成交额一致** ⇒ 均价一致 ⇒ 价格也必须一致。此时价格只允许**绝对**舍入容差
  （0.011 元）。超出即真实错价。
- **两边成交额因份额折算而不可比** ⇒ 均价口径本身不同 ⇒ 价格改用**相对**容差
  （0.5%）。

这个区分是必需的，两个真实案例正好卡在两侧：

- **600519.SH 茅台**：成交额**完全一致**，收盘价差 **0.53 元** → 真实错价，必须抓出。
  （只看相对容差会漏掉它 —— 0.043%。）
- **000170.SH「50AH优选」**：成交额差 1.6%（份额折算所致），收盘价差 1.83 元 → 同一折算的
  副作用，放过。（只看绝对容差会误杀它 —— 高价位净值点位。）

### 判据之间有依赖，顺序不能颠倒

1. **成交量**先比 → 决定两边口径是否可比（单位差 / 份额折算）；
2. **成交额**次之 → 是锚，决定价格用哪种容差；
3. **收盘价**最后 → 按上一步的可比性选容差。

**份额折算一旦成立，成交额也带着同样的折算**，因此成交额不能直接比。三只 LOF 的成交额差
（1.6% / 8.1% / 13.6%）全部源自同一个折算，若不联动就会把这三只正常数据误判成冲突 —— 这正是
规则迭代过程中实际发生过的：初版规则误报 4 个冲突，修正后收敛到 1 个真冲突。

### 份额折算窄带 [90, 120]

LOF 基金的二级市场成交量与基金净值份额不是 1:1，倍数不是整数且随行情漂移，无法用固定常数
归一。实测三个比值 105.4 / 108.7 / 112.4 落在 [90, 120]，而 **399002.SZ 的 65.75 倍落在窄带外**
—— 窄带的选择直接决定了真问题能否被抓出来。

## 二、数据源注册表

`metadata.data_source` 现在是**优先级与独立性的单一事实来源**。

| 源 | 类型 | 优先级 | 独立上游 |
|---|---|---|---|
| `manual` | manual | 10 | 否 |
| `hithink_finance_dump` | vendor | 40 | 否 |
| `csv` | csv | 40 | 否 |
| `hithink_finance` | api | 50 | 否 |
| `hithink_finance_index` | api | 50 | 否 |
| `tdx_official` | vendor | 70 | **是** |
| （未注册源） | — | 90 | — |

**`is_independent` 标记只有真正独立上游的源**。三个同花顺源共享一个上游，它们之间互相印证
证明不了任何东西 —— 一个上游的系统性错误会被三个源同时复制。只有通达信是另一家厂商。

优先级约定：**数字越小越权威**（与 `raw.daily_bar.source_priority` 既有语义一致）。通达信取 70，
高于同花顺各源、低于兜底补录（80）：它参与对账但不抢占主源位置。两个理由：

1. 项目历史数据全部来自同花顺，换主源会造成历史与新数据的口径断层；
2. 通达信指数成交量是「手」而项目是「股」，选它当主源会把单位问题带进可信层。

未注册的源拿到 90（比任何已知源都低），而不是 0 —— 一个刚接入的源不该因为"没登记"就自动成为
最权威的。

## 三、通达信作为独立第二源

`app/data_sources/tdx_official.py` 把通达信官网盘后包归一成项目的 `DailyBarRecord`：

- **只保留项目 `market.security` 里存在的标的**。通达信用 `999999` 表示上证指数而项目用
  `000001.SH`，通达信独有代码不在项目命名空间内，放进来只会制造"项目没有的标的"。
- **成交量不做换算**。原始值原样入库，口径知识集中在对账层处理（实测换算倍数随指数而变：
  541 只 100 倍、2 只 10000 倍、3 只 105–112 倍，写死一个常数必然换错一部分）。
- **过滤无成交的 bar**。实测 688053.SH 等 4 只票 open/high/low 均为 0 而 close 带着发行价 ——
  那是"当日无成交"而不是"厂商发垃圾"，在边界处挡掉，而不是入库后被 `PRICE_INVALID` 拒绝。

## 四、修掉的既有缺陷

### `build_from_raw` 的单源过滤（对账休眠的根因）

```python
# 修复前：比较集合被收窄到单一来源 → 永远只有一个源可比 → 对账表 0 行
raw_groups = self.raw_repository.latest_candidates_by_source(
    ..., source_name=source_name,
)
# 修复后：候选仍由 source_name 限定，但比较集合跨全部来源
raw_groups = self.raw_repository.latest_candidates_by_source(
    ..., source_name=None,
)
```

候选选择与比较集合是两个不同的事：前者决定"谁的数值进可信层"，后者决定"拿谁校验"。混成一个
参数是对账休眠的直接原因。

### `_compare_candidates` 的精确相等判据

原实现用 `getattr(left, f) != getattr(right, f)` 逐字段精确比较，任何亚分差都会被判成冲突。
现改为带容差、带单位归一、且 OHLC 四字段整体检查（收盘价正确但开盘价记错的情况不能漏判）。

## 五、实测抓出的真实数据问题

**399002.SZ「深成指R」成交额差 50.4%** —— 项目侧 412,372,110,000 元，通达信侧
830,819,926,016 元。同一交易日的 399001.SZ「深证成指」与 399106.SZ「深证综指」成交额几乎相同
（830,863,048,704 与 830,861,400,000），说明项目这一天的 399002 数据本身存疑。

这正是引入独立第二源的意义：同花顺的三个接口不可能发现这个问题。

## 六、遗留与后续

1. **`.CSI` 中证指数的日历缺口**（既存，非本次引入）：`000510.CSI` / `000860.CSI` 的
   `exchange=UNKNOWN`，而 `market.trading_calendar` 只覆盖 SH/SZ/BJ，导致每个交易日被记
   `CALENDAR_MISMATCH` 错误。应把中证指数纳入日历或显式标记为非交易日。
2. **`data_quality_issue` 重复写入**：raw 里同一标的存在多个版本时，同一条 issue 会重复写入
   （实测 `.CSI` 两个标的出现 4 次）。issue 表无唯一约束，重跑会持续累积。
3. **通达信只覆盖单日**：目前仅采集了 2026-11-10 一天，跨多日采集需要考虑官网包的保留期限
   （实测 2021-01-04 已 404，2022-05-06 之前无北交所文件）。
4. **`market.valuation_snapshot` 仍只有 4 个交易日** —— 价值因子与选股直接受影响，腾讯行情
   0.2s/批可补，但腾讯 PB 与东财口径已有约 2% 差异，须先对账再入库。这是 P1。
