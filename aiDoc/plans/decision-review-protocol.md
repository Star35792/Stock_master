# 决策与提交评审协议

本协议把多角色讨论变成可判定、可执行的门禁。它用于重大决策和 AI 代办的 Git 提交，不要求普通小改动重复进行完整评审。

## 1. 变更分级

先根据变更语义和影响边界分级，不以改动行数或关键词作为唯一依据。

### T0：无语义变化

- 拼写、格式、注释或纯导航调整。
- 不改变规则含义、运行行为、契约或项目状态描述。

只需常规检查，不启动四角色评审。

### T1：边界内变化

- 局部 bug fix、测试补充或内部重构。
- 已有产品范围和设计内的实现，且不改变外部行为、公共 API、schema、架构边界、数据契约或金融语义。

只做轻量评审；若实际 diff 越过上述边界，立即升级为 T2。

### T2：重大决策

命中任一条件即为 T2：

- 修改项目级 AI 规则、阶段定位、路线优先级、MVP、验收边界或关键用户工作流。
- 在两个以上可行方案中选择会产生长期兼容、迁移、维护或不可逆成本的方案。
- 修改跨模块职责、依赖方向、事实源、数据流、公共 API/契约、schema 或迁移策略。
- 新增或替换关键依赖、基础设施、外部数据源、调度链路或跨模块能力。
- 修改 `raw -> market -> factor -> research/backtest -> portfolio/risk -> trade` 链路的契约、质量、血缘或审计规则。
- 修改因子定义、金融指标口径、可得时间、复权、公司行为、回测假设、费用滑点、组合约束、风控或持仓管理与模拟推演边界。
- 方案可能引入未来函数、样本泄漏、幸存者偏差、错误金融精度、不可交易假设、真实资金风险或难以恢复的数据操作。
- 无法可靠判断属于 T0 或 T1。

规则文件自身的语义变更始终按 T2 处理。纯文案、测试或局部修复只有在确实不改变上述边界时才能排除。

## 2. 四角色共同评审

T2 在确定方案前执行两阶段评审。

第一阶段由四角色独立审查，避免互相锚定：

| 角色 | 必查内容 |
| --- | --- |
| 架构师 | 分层与依赖、模块职责、事实源和数据流、迁移与回退、可测试性、可观测性、演进成本 |
| 产品经理 | 用户价值、当前阶段、MVP 和非目标、优先级、工作流、验收标准、是否过度建设 |
| 金融行业专家 | 时点正确性、数据血缘、复权和公司行为、金融精度、偏差、成本与可交易性、组合风控、审计与资金风险 |
| Vibe Coding 规则编写者 | 触发条件是否可判定、引用式读取、最小改动、测试门槛、文档同步、跨工具可执行性、规则冲突和过度触发 |

每个角色必须输出：`结论（通过/有条件通过/阻断）`、证据、风险等级、建议、需要补充的测试或文档。

第二阶段由主代理汇总分歧，逐项标记 `采纳`、`拒绝` 或 `待用户决策` 并说明理由。架构边界、产品范围或金融风险存在未解冲突时不得静默裁决；会实质改变用户目标的选择必须交由用户决定。

运行环境支持子代理时，四角色应独立执行并尽量并行；并发容量不足时可分批。不支持子代理时，主代理必须按同一模板逐角色完成，并在报告中标记 `fallback: 主代理分角色评审`。

完成评审需同时满足：

- 四个角色结论齐全，冲突已裁决或已取得用户决定。
- 选定方案不违反根 `AGENTS.md`（及其指向的模块 `AGENTS.md`）、可信数据链路和当前产品阶段。
- 验收标准、测试方式、风险、回退方式和文档影响明确。
- P0 阻断项已关闭；P1 只有在用户明确接受，并记录接受理由、后续责任、影响和退出条件时，才可作为附条件提交，不能静默放行。

## 3. 金融项目硬检查

涉及金融、数据、研究、回测、组合、风控或交易时，逐项判断 `通过/不适用/未验证`，不得把未知默认为通过：

- 数据是否遵循 `raw -> market -> factor` 血缘，来源、版本和质量状态是否可追溯。
- 公告时间、采集时间、首次可得时间和信号生效时间是否防止未来函数。
- 复权、公司行为、停牌、涨跌停、上市退市、历史成分和幸存者偏差是否处理正确。
- 核心价格和金额是否保持精确口径；银行、保险、券商等金融行业是否使用独立适用口径，不得直接套用普通工商企业的流动比率、债务率或利息覆盖等指标。
- 回测是否包含费用、滑点、容量、流动性和不可成交条件，并进行样本外或滚动稳定性验证。
- 组合是否有单标的、行业、风格、现金、回撤和风险预算约束，调整原因是否可解释。
- 结果能否按数据、因子、代码和参数版本复现、回放和审计。
- 模拟推演执行是否保留人工确认、限额、幂等与完整审计链路。

任何与当前变更直接相关的 `未验证` 项都必须进入风险或阻断项。

## 4. AI 提交前项目现状评审

当用户要求 AI 执行 `git commit` 或创建 PR 时，提交动作前必须：

1. 读取 `git status` 和 staged diff；未暂存时检查拟提交 diff，不能把无关工作区变更混入评审或提交。
2. 重新执行 T0/T1/T2 分级，并读取根 `AGENTS.md`、受影响模块的 `AGENTS.md`、`aiDoc/README.md`、`aiDoc/plans/README.md` 和受影响边界的 reference。
3. 核对变更与当前阶段、近期优先级、架构、金融语义、测试、文档同步和敏感信息的一致性。
4. T2 若没有针对当前需求和当前 diff 的有效四角色评审，先补做完整评审；T0/T1 只做轻量检查。
5. 输出项目现状评审报告后，才能决定是否执行提交。

同一任务、同一决策和实质相同的 diff 不重复评审。需求、候选方案、架构前提或 staged diff 发生实质变化时，原评审失效并重新执行。无需为此创建缓存文件。

### 风险与建议分级

- `P0 阻断`：数据损坏、安全问题、金融正确性、未来函数、资金风险、违反项目不变量；关闭前不得提交，用户确认也不能绕过。
- `P1 必须处理`：由本次变更直接造成的契约、测试、迁移、文档或验收缺口，默认提交前关闭；只有用户明确接受，并记录接受理由、后续责任、影响和退出条件时才可保留，此时最终结论必须标为“附条件允许提交”。
- `P2 建议`：不影响本次正确性和验收的优化；不阻止提交，不自动扩大当前任务范围。

每条问题或建议必须包含证据位置、影响和具体动作。非阻断优化建议最多 3 条，并区分“本次必做”和“后续候选”。

### 固定报告模板

```text
提交前项目现状评审
- 变更目标与分级：
- 触发原因：
- 当前阶段与近期优先级：
- 受影响模块和文档：
- 架构师结论：
- 产品经理结论：
- 金融行业专家结论：
- Vibe Coding 规则编写者结论：
- 金融硬检查：
- P0/P1 阻断项：
- P2 优化建议（最多 3 条）：
- 测试与验证：
- 文档同步：
- 明确不做：
- 最终结论：允许提交 / 修正后提交 / 禁止提交
```

T0/T1 的轻量报告可以合并四角色字段，但仍需说明分级理由、测试结果、文档影响和最终结论。

## 5. 记录与能力边界

- 临时讨论和普通提交评审保留在当前任务、提交说明或 PR 中，不为每次评审创建 Markdown 文件。
- 只有会约束后续实现的稳定结论才同步到对应 `aiDoc`；路线变化写入 roadmap，架构变化写入 relations，数据和金融契约写入 data/research，长期偏好写入 memory。
- 评审给出建议但不自动实施非阻断优化；评审不能替代测试、代码审查或用户对高风险动作的授权。
- 本协议只能约束读取本仓库规则的 AI。若要强制拦截用户、IDE 或其他工具的手工提交，需要另行实现 Git hook 或 CI；确定性 hook 也不能替代需要上下文判断的智能优化建议。
